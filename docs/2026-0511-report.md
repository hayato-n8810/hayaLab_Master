# 実装進捗レポート — 2026-05-11

## 概要

JavaScriptマイクロベンチマーク（before→after実装対）を対象に，
GumTreeによるAST差分を起点として **「パフォーマンス変換パターンを機械的に照合するためのコードスコープ」** を決定し，
そのスコープを用いてパターンを集約する一連のパイプラインを実装した．

---

## 1. 粒度選択（`experiments/pattern/decide_granularity.py`）

### 1.1 問題設定

GumTreeが出力するAST差分（`base_actions`）は操作の最小単位に分解されているため，
「差分ノードを含む意味ある処理断片」として扱うには粒度が細かすぎる．
一方で，差分を含むブロック全体（関数スコープ等）は冗長すぎる．

**目標**：差分を含む最小の「意味ある処理断片」を機械的に選ぶ．

### 1.2 候補スコープの設計

差分を起点として包含関係が成立する4段階のスコープを設計した：

```
DIFF ⊆ BROTHER ⊆ EXCL ⊆ INCL
```

| スコープ名 | 定義 | 直感 |
|---|---|---|
| `merged_diff` | GumTree差分ノードをそのままマージ | 変更箇所そのもの |
| `merged_brother` | 差分ノードの兄弟ノードまで拡張 | 差分の文脈（同列の演算子等）を含む |
| `merged_excl` | 差分を含むブロック（差分ノードの親ブロック）の外側 | ブロック境界まで広げる |
| `merged_incl` | 差分を内包するブロックごと含む | より広い制御フロー構造を含む |

包含の小さい順（DIFF → INCL）に候補を列挙することで，後の重複除去が「小さいスコープを優先して残す」という性質を持つ．

### 1.3 前処理（フィルタリング・重複除去）

**記号のみ候補の除去**

差分が括弧や演算子だけで構成されるケースは，文字列検索クエリが空になり判定不能になるため除外する．
除外対象は以下のいずれかに該当する終端トークンのみからなる候補：

- `string_fragment`, `escape_sequence`, `number` という node name
- `VAR_*`, `FUNCTION_*`, `KEY_*` の抽象化変数
- 汎用記号・宣言キーワード（`(`, `)`, `,`, `;`, `{`, `}`, `var`, `let`, `const` 等）

**重複除去**

`origin_index` の frozenset が完全一致する候補は同一のノード集合とみなして1つに集約する．
per_action が1件しかない場合は `merged_diff` と `merged_brother` が同一ノード集合になる，
このような冗長な候補を事前に削除する．

### 1.4 スコアリング設計とその思想

#### Hard Constraint: `str_R = 1`

各候補スコープの全終端トークン値を `\s*` で繋いだ正規表現を生成し，
元プログラムの `base_ast.code` にマッチするかを確認する（`re.search`）．

**採用理由**：AST差分から切り出したノード列が元コード上で連続した処理断片として成立するかを確かめるための最小チェック．
`\s*` を区切りにするのは，JSコードではトークン間に改行・スペースが任意に入るためで，
`.*` では行をまたぐノイズが多くなりすぎる（`re.DOTALL` を使用）．

このConstraintを満たさない候補は選択対象から除外する．

#### スコア：調和平均 `score = 2 * diff_ratio * sibling_completeness / (diff_ratio + sibling_completeness)`

2つの指標の引っ張り合いを調和平均で統合する設計：

**diff_ratio** = `|diff_nodes| / |scope_nodes|`

- スコープ内に占める差分ノードの割合
- スコープが小さいほど高く（1.0に近く），大きいほど低下する
- 「差分を薄める方向」への圧力

**sibling_completeness** = 差分ノードの直接親ごとに「全直接子のうちスコープに含まれる割合」を平均したもの

- 差分ノードの親の直接子を全AST（スコープ外も含む）から探し，scope内に何割含まれているかを測る
- スコープが大きいほど高くなる傾向がある
- 「差分周辺の兄弟ノードを揃える方向」への圧力

**なぜ調和平均か**：

算術平均では一方が極端に大きければ他方が低くても補填される．
調和平均は「両者ともゼロでない中間値」を好む性質があり，
「差分が密 **かつ** 差分周辺の兄弟が揃っている」スコープに最高スコアが付く．
この2つの要求を同時に満たさないとスコアが上がらない点が設計意図と一致している．

### 1.5 なぜこの手法を選んだか（設計に至った経緯）

当初はコーパス（MBDiff.json 29809件）に対するAST bigram AND検索の「ヒット数最小 + 対象IDにヒット」という
情報検索的なアプローチ（relative selection by corpus search）を検討していた．

しかし以下の課題が生じた：
- コーパス全体への検索はプロセス並列化しても29809件×候補数の組み合わせで計算が重い
- ヒット数は候補スコープの内容に依存するが，「対象IDへのヒット」という条件は全候補で概ね満たされ，差異が出にくいケースがある

そこで **スコープの構造的な性質だけでスコアを計算できる指標設計** に切り替えた．
`diff_ratio`（純粋にノード数比）と `sibling_completeness`（全ASTを参照するが追加コーパス検索は不要）の組み合わせは，
外部データベース検索なしで各IDを独立に処理でき，`ProcessPoolExecutor` による並列化も自然に成立する．

`str_R` による Hard Constraint は，コーパス検索の役割の一部（「元コード上に成立するか」の確認）を局所的に果たす代替として残した．

## 2. パターン集約

### 2.1 設計方針

粒度選択で得られた `selected.nodes`（スコープ内のASTノード集合）を入力に，
14IDのパターン間距離行列を計算し，階層クラスタリングで集約する．

評価の基準として，ユーザーが手動でラベル付けした「理想クラスタリング」を利用する：

| ラベル | 該当ID | 共通パターン |
|---|---|---|
| A | 222 | for-in ループ |
| B | 609, 791, 902, 1691 | reduce + arrow_function |
| C | 1206, 1306 | `String` 型変換 |
| D | 2512, 2919 | `toString.call` チェーン |
| E | 6182, 14412, 21294, 23864 | substr / 文字列加工 |
| F | 8126 | split-join パターン |

### 2.2 共通インフラ（`_common.py`）

全アルゴリズムに共通する処理を提供：

- **`PatternTree`**: `selected.nodes` からスコープ内部の親子関係を再構築した部分木（forest）
- **`flatten_tokens`**: preorder traversal でノードを1つのトークン列に変換（記号除去オプション付き）
- **`build_forest`**: `parent` パス列の in-scope 最近祖先を「直接親」として部分木を再構築
- **正規化バリアント** (`none` / `supertype` / `custom`): ノード名のグループ化段階を切り替え
- **`cluster_from_distance`**: 距離行列 → linkage（average法）→ k=2〜9のラベル列
- **`save_result`**: 全アルゴで統一した JSON スキーマで保存

抽象化トークン（`VAR_0`, `FUNCTION_1`, `KEY_2`）は `<VAR>`, `<FUNC>`, `<KEY>` に変換済み（元コードが変数名・関数名を抽象化している前提）．

## 3. 比較アルゴリズム一覧

### 3.1 実装済みアルゴリズム

| アルゴリズム | 実装ファイル | 距離定義 | 特徴 |
|---|---|---|---|
| NiCad | `algo_nicad.py` | トークン列 Levenshtein 比率距離 | 順序保持・記号除去・識別子抽象化 |
| Deckard | `algo_deckard.py` | ノード型ヒストグラム Cosine 距離 | 順序非依存・型分布を表現 |
| SourcererCC | `algo_sourcerercc.py` | multiset Jaccard 距離 | 順序非依存・包含関係に寛容 |
| APTED | `algo_apted.py` | 厳密 Tree Edit Distance（最大サイズ正規化） | 木構造の違いを最も忠実に距離化 |
| path_context | `algo_path_context.py` | leaf-leaf パスの bag-of-paths Jaccard | 構造的近傍関係を反映 |
| proposed | `algo_proposed.py` | 多特徴重み付き和（struct/method/keyword/literal） | 各軸の特性を混合 |
| abst_hier | `algo_abstraction_hierarchy.py` | 抽象化レベル階層による距離（Mode A/B/C） | 段階的な抽象化で等価判定 |

### 3.2 各アルゴリズムの設計思想と性質

#### NiCad（NiCad 風: Levenshtein比率距離）

Roy & Cordy (ICPC 2008) の手法に基づく．
「正規化されたトークン列を直列化して Levenshtein 距離で比較する」ことで，
**順序を保持したまま差分を距離に変換**する．

- 強み: トークンの並び順の違い（`a[i] = b[i]` vs `b[i] = a[i]`）を捕捉できる
- 弱み: 包含関係（902⊂791，片方が片方のサブセット）では挿入コスト分の距離が出やすい
- 適した検出ケース: 「1〜2トークンだけ違う」Type-2クローン

#### Deckard（ノード型ヒストグラム + Cosine）

Jiang+ (ICSE 2007) の手法に基づく．
各スコープを「ノード型の出現回数ベクトル」に潰してコサイン距離で比較する．

- 強み: `1206` vs `1306`（リテラル値だけ違い，構造が同一）で距離ほぼ 0 になる
- 弱み: 順序情報を完全に捨てるため，同じノードの並び替えが区別できない
- 適した検出ケース: 構造が同一でリテラルだけ異なる Type-2 クローン

#### SourcererCC（multiset Jaccard）

Sajnani+ (ICSE 2016) の手法に基づく．
トークンを multiset として Jaccard 類似度を計算する．

- 強み: 包含関係（`902 ⊂ 791`）に最も寛容（片方が他方を完全に含む場合 Jaccard = `|A|/|B|`）
- 弱み: 出現順序の違いを区別しない
- 適した検出ケース: 部分的に重複するコードフラグメントのクローン検出

#### APTED（厳密 Tree Edit Distance）

Pawlik & Augsten (VLDB 2015) による最適 TED アルゴリズム．
木の挿入・削除・置換コストの最小和を計算し，最大サイズで正規化する．

- 強み: 構造の違いを最も忠実に距離化する；全アルゴ中「構造上の真の近さ」に最も近い
- 弱み: 意味的に等価でも構造が異なる（`split().join()` vs `replaceAll()`）には距離が出る
- 計算量: O(n³) だが N=14, n≤49 程度なら問題なし

#### path_context（leaf-leaf パスの bag-of-paths Jaccard）

code2vec (Alon+ POPL 2019) の path-context 表現に基づく．
2終端ノード間の最短木パスを文字列化して bag-of-paths を構成し，Jaccard 距離を計算する．

- 強み: 「ループの中で呼ばれた reduce」vs「関数引数での reduce」といった構造的文脈を区別できる
- 弱み: 全終端ペアを列挙するため特徴空間が n² オーダーになる；スコープが大きいほど不安定になりやすい
- 実装上の工夫: `MAX_LEAF_PAIRS=800` で等間隔サブサンプリングし決定的に制限

#### proposed（多特徴重み付き和）

4軸の重み付き和として距離を定義する：

```
d(i,j) = 0.45 * d_struct + 0.30 * d_method + 0.15 * d_keyword + 0.10 * d_literal
```

- `d_struct`: 正規化トークン列の Levenshtein 比率距離（NiCad と同形だが正規化粒度が違う）
- `d_method`: `property_identifier` や組み込み識別子名の集合 Jaccard 距離
- `d_keyword`: JS キーワード（for/while/return等）の集合 Jaccard 距離
- `d_literal`: 数値・文字列リテラルの集合 Jaccard 距離

各単独軸が突出するケースでは他の専門手法に劣るが，複合的にバランスする設計．

#### abst_hier（抽象化レベル階層）

proposed の発展版として設計した手法．重み付き和ではなく，
**段階的な抽象化レベル（L0〜L5）での等価性チェック**で類似度を測る：

| Level | 識別子タグ | リテラル | API/組み込み | 構造ノード名 | 相当クローン型 |
|---|---|---|---|---|---|
| L0 | `<VAR>/<FUNC>/<KEY>` | 値そのまま | 値そのまま | 名前そのまま | Type-1 |
| L1 | same | `<LIT>` | 値そのまま | 名前そのまま | Type-2 (lit-only) |
| L2 | `<TERM>` | `<TERM>` | 値そのまま | 名前そのまま | Type-2 (lit+id) |
| L3 | same | same | `<API>` | 名前そのまま | Type-3 (API抽象) |
| L4 | same | same | same | 正規化グループ名 | Type-3 (構造同型) |
| L5 | same | same | `<API>` | `<STRUCT>` | Type-4 (骨格のみ) |

距離計算には3つのModeを実装した：

- **Mode A**: 最初に「等価とみなせるレベル k」をε-近似で判定し `k/(K-1)` を距離とする（dendrogramの高さ = 必要な抽象化深度に対応）
- **Mode B**: 全レベルでの正規化 Levenshtein 距離の最小値（パラメータ無し）
- **Mode C**: Mode A の連続版；`(k + Lev_k/max_len_k) / k_total` で端数を持たせる

`keep_literal` フラグにより，L0（リテラル保持）をスキップするかどうかを切り替えられる．
ε感度分析により，ε ∈ {0.0, 0.1, ..., 0.6} の各値での ARI を比較する機能も実装済み．

## 4. 評価方法

### 4.1 評価指標

**Adjusted Rand Index (ARI)**

理想ラベル（A〜F）と各アルゴリズムの k クラスタリングの一致度を ARI で定量評価する．
ARI ∈ [-1, 1]；完全一致 = 1.0，ランダム期待値 = 0.0．

k=6（理想クラスタ数と同じ）での評価と，k=2〜9のうち最大 ARI を与える k での評価（k自由）の両方を計算する．

**per-class Jaccard**

理想ラベルの各クラス（A〜F）について，最もよくマッチするクラスタとの Jaccard 係数を計算する．
クラスごとの回収性能の把握に使う．

### 4.2 観察ケース

以下の特定ペアについて，各アルゴリズムの距離と dendrogram 上での結合高さを追跡する：

| ケース名 | ペア | 観察内容 |
|---|---|---|
| subsumption_902_in_791 | 902 vs 791 | 包含関係（902のスコープが791に内包される）をどう扱うか |
| literal_only_1206_1306 | 1206 vs 1306 | リテラル値だけが異なる構造同一ペア |
| syntactic_synonym_2512_2919 | 2512 vs 2919 | toString.call チェーンの記号的同義 |
| char_at_14412_23864 | 14412 vs 23864 | 共に substr(*,1) パターン |
| reduce_family_609_902 | 609 vs 902 | reduce 同士だが意味が異なるケース |
| string_slice_8126_21294 | 8126 vs 21294 | 共に文字列加工だが手法が異なるケース |

### 4.3 正規化バリアントの効果

`none` → `supertype` → `custom` と進むほど異なる構文が同じ構造として扱われる傾向がある．

- `supertype`: tree-sitter の公式スーパータイプグループ（`primary_expression` 等）を使う．
  範囲が広すぎて「数値リテラルとメンバ式」が同一視されるケースがあり，ノイズが増えることがある．
- `custom`: `function_like`/`var_decl_like`/`loop_like`/`member_access_like` 等を手動で定義した小さなグループ．
  同族ペア（特に1206/1306）の結合高さを下げる傾向があり，より意図した粒度でのグループ化ができる．

## 5. アルゴリズム比較の設計上のトレードオフ

| 問題ケース | 強いアルゴ | 弱いアルゴ | 理由 |
|---|---|---|---|
| リテラルだけ違う（1206 vs 1306） | Deckard (cosine) | NiCad, APTED | ヒストグラムは同一；Levは編集1個分の距離が出る |
| 包含関係（902 ⊂ 791） | SourcererCC | Deckard, APTED | Overlap類似度；ベクトル長の違いが出ない |
| 構造的文脈の違い（reduce の使われ方） | path_context | SourcererCC | パスが構造的近傍を反映；bag-of-tokenは文脈を捨てる |
| 総合バランス | proposed, abst_hier | 各専門手法 | 複合指標で極端なケースを丸める |

**提案手法（proposed / abst_hier）の位置付け**：

単独軸に特化した既存手法（NiCad/Deckard/SourcererCC/APTED）はそれぞれ特定のクローン型に強い．
`proposed` はこれらの特性を重み付き和で混ぜることで「どの局面でも大きく外れない」ことを目指す設計．
`abst_hier` はさらに抽象化の段階を明示的に管理し，dendrogram の高さに「どのレベルの抽象化が必要か」を
読み取れるようにする設計で，解釈可能性が高い．
