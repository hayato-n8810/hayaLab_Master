# LLM 高速化修正学習: 学習方法・方針 草案

作成日: 2026-07-06。手法空間の調査と設計議論は `docs/framework_design_options.md` を参照。本書は候補となる各方向について、**その方向で進める場合に成立していなければならない前提と、必要になる処理**を方向ごとに自己完結でまとめたもの。

- タスク: JavaScript コード断片 x（+ setup 文脈）から、観測等価でより高速な書き換え y を生成する（「意味保存」とは主張しない）。
- データ: jsPerf（実行可能 2 変種以上 13,054 ベンチ / 43,244 プログラム）。学習単位は常に 1 ベンチ内で完結させ、ベンチ間で速度を比較しない。

---

## 方向 1: タグ条件付き SFT（PIE 型）— ベースライン・保険

**前提**

- ベンチ内相対 speedup が安定して測れる（計測ハーネスの K/N/M が決定済みで、有意差の出るペアが相応にある）。
- アンカー → ターゲットのペアが「書き換え」として意味を持つ、つまり両者が最低限等価（E1 以上）であること。タグ SFT 自体は等価性なしでも回るが、非等価ペアを教えると挙動破壊を学習する。
- 数万ペア規模で 7B + LoRA の SFT が成立する。

**必要処理**

1. 計測ハーネス（step6）で全変種を計測 → ベンチ内相対 speedup を算出
2. speedup のビン分割とタグ語彙の設計（例: 10 段階）
3. 単入力差分テストによる最低限の等価フィルタ（E1 以上のみ採用）
4. アンカー選択 → (x, tag, y) 形式のペア構築
5. SFT（LoRA）学習・推論時は最高速タグを指定

**この前提が崩れたら**: 最も頑健な方向であり、これが成立しないならデータ自体が学習に向かない（研究計画の見直し）。

---

## 方向 2: 棄却サンプリング自己蒸留（RAFT / ReST-EM 型）

**前提**

- 生成候補の自動検証（差分テスト + 粗い速度計測）が無人で回る実行基盤がある。
- 初期モデルに「たまに当たる」程度の生成能力がある（当たり率ゼロなら蒸留素材が得られない）。
- 反復あたりの計測予算が見積もれている。

**必要処理**

1. 初期モデル（方向 1 の成果物など）で 1 入力あたり k 候補を生成
2. 生成物への自動等価チェック（多入力差分テスト）+ 速度計測
3. 「等価∧入力より X% 高速」通過品のみで再 SFT、閾値 X を反復ごとに引き上げ
4. 反復ごとの合格率・計測コストのトラッキング

**この前提が崩れたら**: 当たり率が低すぎる場合は方向 1 で底上げしてから再試行。検証基盤は方向 8 と共通なので投資は無駄にならない。

---

## 方向 3: 二値ペア選好（素の DPO / IPO / KTO）— 比較用ベースライン

**前提**

- ベンチ内に統計的に有意な速度差を持つ 2 変種ペアが十分数ある（tie ばかりならペアが組めない）。
- chosen/rejected の類似度が Smaug / Likelihood Displacement の失敗域（高類似ペアでの尤度崩壊）に入っていない — **パイロット P1（トークン重複率分布）の結果に依存**。
- ペアの等価性ラベル（E1 以上）が付いている。

**必要処理**

1. 計測 + 有意差判定 → chosen（速）/ rejected（遅）ペア化
2. CHES スコア等によるデータ診断、SFT 項併用の設計
3. DPO 学習（提案手法の対照として）

**この前提が崩れたら**: P1 で高類似ペアが支配的と分かった場合、素の DPO の失敗自体が論文の主張材料になる（提案手法の動機付けに転用）。

---

## 方向 4: マルチ条件ランキング学習 — 主提案

サブ分岐: **4a 段階付き包含**（E−1 を最下位集合として学習に含める）/ **4b 等価ゲート**（E2/E1 のみで学習）。4a vs 4b は ablation として両方実施する。

**前提**

- ベンチ内**全ペア**の差分テストが自動化できる: 出力観測手段（stdout・終了時変数値の計装）がスニペットの大半に適用可能 — **パイロット P2（等価ラベル歩留まり）で検証**。
- 多入力生成（E2 判定）が一定割合で自動化できる（自由変数の特定と変異）。
- 有意差ペアが十分ある — **パイロット P3（有意差歩留まり）で検証**。tie だらけなら listwise の利得が消える。
- 3 変種以上のベンチが相応にある（実測 48% — 確認済み）。
- 4a 固有: E−1 ラベルの信頼性。自己再実行一致（self-agreement）チェックで非決定的コードを E0 に隔離でき、E−1 が「再現性のある食い違い」に限定できること。

**必要処理**

1. self-agreement チェック → 非決定的コードを E0 へ隔離
2. ベンチ内全ペアの単入力差分テスト（E1 判定）→ 入力変異による多入力化（E2 判定）
3. 挙動クラス分割 → アンカー選択 → リスト構築
   - 4a: 等価群を速度順に並べ、E−1 群を**順序なしの最下位集合**として付加（E−1 同士に速度順序は付けない）
   - 4b: 等価群のみでリスト構築
4. 計測 → ベンチ内相対マージン log(speedup) と信頼区間による tie 判定
5. ペア重みの実装（等価証拠 E2/E1 × 速度差の統計的信頼度。**ランクは 2 値、E1/E2 の差は重み**）
6. listwise（LambdaLoss / PRO 型）と pairwise を同一定式化の特殊化として実装、学習
7. 尤度崩壊対策（SFT 項併用 or DPOP 型保護）と CHES 診断

**この前提が崩れたら**: P2 の歩留まりが低い場合は 4b すら成立せず、等価性を要求しない方向 1 が主軸に繰り上がる。P3 が低い場合はマージン・listwise を捨て順位のみの学習に縮退。

## 方向 5: diff マスク（トークン重み付け）— 付加部品

**前提**

- **変種ペアのトークン重複が高い**（信号が差分に局在する）— **パイロット P1 が採否の判定条件**。jsPerf の変種は独立実装であり、逐次編集データ（PIE 等）と違って重複が低い可能性がある。重複が低ければマスク ≒ マスクなしで貢献が空洞化する。
- GumTree / Myers diff が JS スニペットに安定適用できる（パース成功率）。
- AST diff とトークナイザのサブワード列の整列が実装できる。

**必要処理**

1. P1: ベンチ内変種ペアのトークン重複率・正規化編集距離の分布計測（step1 出力のみで実施可能）
2. ペアごとの diff 抽出 → トークンレベルマスクへの変換・サブワード整列
3. マスク重み付き損失の実装（方向 3/4 のどちらにも装着可能）
4. マスク有無の ablation

**この前提が崩れたら**: 部品ごと廃棄し、方向 4 の条件構造 + 重み設計を単独の技術コアとする（草案全体は壊れない）。

## 方向 6: 恒等アンカー — 付加部品（仮説）

**前提**

- コピー縮退（入力複写への崩壊）が実際に起こること。これは変種間のトークン重複が高い場合に深刻化するため、**方向 5 と同じく P1 に依存**。
- アンカーの順位位置（等価∧低速の上に置くか下に置くか）が定義されていること。(高速 ≻ 恒等) は複写を抑制する一方 (恒等 ≻ 低速) は複写を報酬する両刃であり、「縮退対策」と先験的には主張できない。

**必要処理**

1. リスト構築時に入力複写を speedup=1.0・E2 扱いの疑似変種として注入
2. 学習後の no-op 出力率など、縮退の観測指標を定義・計測
3. 有無・位置の ablation

**この前提が崩れたら**: 部品ごと廃棄。観測指標（no-op 率）は残す価値がある。

## 方向 7: 別建てランカー（報酬モデル）+ generate-then-rank

**前提**

- 方向 4 の処理 1〜4（E ラベル付きペア）が完了している。特に **E−1 データが必須**（非等価候補を降格する能力は非等価負例なしには学習できない → 4b のみ採用した場合この方向は弱体化する）。
- ランカーと生成方策の学習データ分割が設計されている（同一データで両方を学習すると RQ2 の評価が記憶の測定になる）。
- 転移先（EffiBench-X JS）の入力形式にランカーが適用できる。

**必要処理**

1. Bradley-Terry / rank 損失の軽量ランキングモデルを**ベンチ内ペアのみ**で学習（方策の logprob 流用はしない）
2. 生成 k 候補 → ランカー上位 m 選抜 → 実測検証の評価パイプ実装
3. 評価: valid coverage@m を「ランダム選抜」「実行オラクル選抜（上限）」と比較
4. 転移実験: 同一下流タスクで「方策単独 vs ベースモデル + ランカー選抜 vs 併用」を比較

**この前提が崩れたら**: RQ2 は素の best-of-k（実行検証つき）評価に縮退。RQ3 の「方策 vs 批評家」の問いは失われる。

---

## 方向 8: オンライン RL（GRPO）— 副次分析

**前提**

- ロールアウトごとの報酬付与が現実的コストで可能であること。すなわち (a) 粗い 1 発計測で報酬として十分、または (b) 方向 7 のランカーが報酬プロキシとして機能する。フル精度計測（warmup + 多ラウンド + pinning）を毎候補に行うのは非現実的（12 万候補規模）。
- 等価チェックの高速化（ベンチごとの入力セット・期待出力のキャッシュ）。
- RL 基盤（verl 等）と計測環境の分離（pinning と GPU 学習の干渉回避）。

**必要処理**

1. 報酬関数の実装（非等価 = 固定負値、等価 = tanh(ベンチ内相対 speedup)。グループ内正規化はベンチ内比較の制約と整合）
2. 非同期報酬ワーカー（計測キュー）の構築
3. 小規模サブセットでの GRPO 実行、Phase 2（方向 4）モデルとの比較

**この前提が崩れたら**: 実施しない。Afterburner が既にパラダイム比較を行っているため、本研究の主張は方向 4 の ablation だけで自立する設計にしておく。

## 前提の依存関係まとめ

| パイロット | 検証内容 | 採否が決まる方向 |
|---|---|---|
| **P1** トークン重複率分布 | 「信号は差分に局在」「コピー縮退が起こる」の成否 | 方向 5・6（採否）、方向 3（失敗域の診断） |
| **P2** 等価ラベル歩留まり | 差分テスト・多入力化の適用率、E2/E1/E0/E−1 比率 | 方向 4（成立可否と 4a/4b の比重）、方向 7 |
| **P3** 有意差ペア歩留まり | 統計的に有意な速度差を持つペアの割合 | 方向 3・4（マージン/listwise の利得）|
| 計測ハーネス確定（K/N/M） | すべての速度ラベルの信頼性 | 全方向 |

| 方向 | 役割 | 主な依存 |
|---|---|---|
| 1 タグ SFT | ベースライン・保険 | 計測のみ（+ 最低限の E1） |
| 2 自己蒸留 | 拡張・検証基盤の先行投資 | 実行基盤、方向 1 の成果物 |
| 3 二値 DPO | 比較用ベースライン | P1・P3 |
| 4 マルチ条件ランキング | **主提案** | P2・P3 |
| 5 diff マスク | 付加部品（仮説） | **P1** |
| 6 恒等アンカー | 付加部品（仮説） | **P1** |
| 7 ランカー + generate-then-rank | RQ2/RQ3 の主役 | 方向 4 の処理、データ分割設計 |
| 8 GRPO | 副次分析 | 方向 7 または粗い計測の許容 |

## 学習タスクから除外するもの（方向を問わず）

- 要因説明（V8 機構ラベル）の学習ヘッド。V8 計測はコンパイラバージョン依存のため学習に使わない既定方針と矛盾する。機構分析は評価・考察章で行う。

## 未決事項

- アンカー選択方針（全変種か最遅のみか — データ量と重複のトレードオフ）
- tie 判定の具体的閾値（K/N/M 決定に依存）
- E1/E2 のペア重みの具体値（P2 の結果を見てから）
- 生成時の入力形式（setup をプロンプトに含めるか。EffiBench-X 転移時の形式との整合）
- ベースモデル選定（Qwen 系 coder 7B 級を第一候補）
