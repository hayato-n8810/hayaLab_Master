# E4. 集約失敗事例の分析 — Isolated と Unigram クラスと巨大クラス

## 1. 目的

自動抽出には限界がある。 本レポートでは集約結果の中で 「集約に失敗する事例」 と 「集約はされるが既知パターンに該当しない巨大クラス」 を分析する:

- **(A) Isolated** = 1 メンバのみのクラス。 希少 bigram を持つため類似閾値を超える相手が居なかった事例
- **(B) Unigram (U1) クラス** = 1 トークン事例の完全一致集約クラスタ。 v7 三本立て化で新設された系統
- **(C) 巨大クラス (size ≥ 100)** = サイズ的に目立つクラス、 既知由来率が低いものはノイズ候補

paper §6.2「クラス数と集約されなかったもの」 への主データ。

**v7 注記**: 旧 v6 では空 bigram 強制 Jaccard=1.0 で 1 つの巨大擬似クラスタ (`L0_M2_9c43d97c`、 1,487 件、 既知由来 0 件) が出現していたが、 v7 三本立て化で **完全に解消された** (空 bigram は excluded、 1 トークン事例は U1 クラスへ独立集約)。

---

## 2. 用語と指標

| 用語 | 定義 |
|---|---|
| **isolated** | メンバ数が 1 のクラス (= singleton クラス) |
| **clustered** | メンバ数が 2 以上のクラス |
| **bigram 集合サイズ** | 各実装対のトークン列から作った bigram 集合のサイズ |
| **文書頻度 (df)** | コーパス 29,809 件中、 当該 bigram を含む実装対の数 |
| **平均 df** | 各実装対の bigram の平均文書頻度。 大きいほど 「ありふれた bigram」、 小さいほど 「希少な bigram」 |
| **M2 クラス** | bigram Jaccard 集約由来のクラス (`L*_M2_*`)、 メンバは 2 トークン以上 |
| **U1 クラス** | unigram 完全一致集約由来のクラス (`L*_U1_*`)、 メンバは 1 トークンのみ |

### 4.2 観察

#### 4.2.1 「Isolated = 短い」 は誤り

Diff / Brother / ExParent では **isolated の bigram 中央値が clustered より大きい** (例: τ=0.7 Diff で 16 vs 13)。 isolated の事例は 「短いから孤立した」 のではなく **「むしろ長く、 ただし他に類似した相手がいない」**。

#### 4.2.2 Isolated は希少 bigram を含む (= 平均 df が低い)

| サイズ | τ=0.7 isolated df | τ=0.7 clustered df | 差 |
|---|---:|---:|---:|
| Diff | 2,411 | 2,800 | -14 % |
| Brother | 3,397 | 3,646 | -7 % |
| ExParent | 3,514 | 3,987 | -12 % |
| Parent | 5,719 | 5,941 | -4 % |

→ **isolated は 「希少な構造を持つ事例」** であり、 paper §6.3.2 で新規パターン候補として扱う対象。

#### 4.2.3 bg=0 (空 bigram) の正体 — U1 クラス由来

旧 v6 では bg=0 (= 0/1 トークンの空 bigram) は singleton にゼロ、 巨大擬似クラスタ `L0_M2_9c43d97c` に吸収されていた。 v7 では bg=0 は U1 クラス (unigram 完全一致集約) に分離され、 isolated にも 115 件 (Diff)、 42 件 (Brother) 等が出現する:

| サイズ | iso bg=0 (U1 singleton) | clu bg=0 (U1 multi-member) | 合計 (= unigram 事例総数) |
|---|---:|---:|---:|
| Diff | 115 | 1,237 | 1,352 |
| Brother | 42 | 199 | 241 |
| ExParent | 2 | 16 | 18 |
| Parent | 0 | 0 | 0 |

→ サイズが広いほど unigram 事例は減る (Parent では unigram=0)。 旧 v6 で 1 つに集約されていた 1,352 件 (Diff) が、 v7 では細分化され singleton 115 件 + multi クラスメンバ 1,237 件に分かれている。

### 5.2 観察

- **U1 クラスのメンバは既知パターン由来が 1 件も無い** — 1 トークンのみの事例 (数値リテラル / 変数スロット / identifier 等) は性能差要因として弱く、 paper §preanalysis の 7 種既知パターンには対応しない

- **サイズを広げるほど U1 クラス数は急減** (Diff 260 → Brother 86 → ExParent 6 → Parent 0)

U1 クラスは **「自動抽出の対象とはなるが、 性能差要因としては機能しない」** 系統。 paper §6.4 妥当性脅威で 「最小限の構造 (2 トークン以上の bigram) を持たない 1,352 件は U1 クラスで分離され、 性能パターンとしての価値は薄い」 と明記。

旧 v6 で問題視した `L0_M2_9c43d97c` (1,487 件擬似クラスタ) は、 v7 では excluded (135 件) + U1 クラス (1,352 件) に分離され、 解釈の透明性が向上した。

## 6.5 U1 クラスメンバのサイズ遷移分析

**問**: L0 Diff の U1 クラス (260 個、 メンバ計 1,352 件) のメンバは、 サイズを Brother / ExParent / Parent に広げたとき、 **同じクラスに所属し続けるか? それとも別のクラスに分散するか?**

各 U1 クラスのメンバ mb_id を、 他 depth の class_id に対応付けて集計した (τ=0.7、 L=0、 出力 `E4_unigram_size_transition.csv`)。

### 6.5.1 全体集計 (260 個の L0 Diff U1 クラスの行き先)

| 遷移先 depth | 1 クラスにまとまる U1 数 | M2 のみへ | U1 のみへ | 混在 (M2+U1) |
|---|---:|---:|---:|---:|
| **Brother** | **189 (72.7 %)** | 174 (66.9 %) | 59 (22.7 %) | 27 (10.4 %) |
| **ExParent** | 170 (65.4 %) | **254 (97.7 %)** | 3 (1.2 %) | 3 (1.2 %) |
| **Parent** | 161 (61.9 %) | **260 (100 %)** | 0 | 0 |

#### 観察

- **「サイズを広げると U1 クラスは概ね 1 クラスにまとまる」**: 60-73 % の U1 クラスが、 他 depth で 1 つの class に集約される (n_destinations = 1)
- **「サイズを広げると U1 → M2 へ昇格する」**: Brother で 67 %、 ExParent で 98 %、 Parent で **100 %** の U1 クラスが bigram あり M2 クラスへ昇格 (= 文脈追加で 2 トークン以上確保される)
- **Parent では U1 クラスが完全消滅** (E2 §4.1 で確認した `Parent で unigram=0` と整合)

### 6.5.2 分散数 (n_destinations) の分布 — Brother への遷移

| 分散数 | U1 クラス数 | 割合 |
|---:|---:|---:|
| 1 個 (1 クラスにまとまる) | 189 | **72.7 %** |
| 2 個 | 33 | 12.7 % |
| 3 個 | 10 | 3.8 % |
| 4 個 | 5 | 1.9 % |
| 5 個 | 5 | 1.9 % |
| 6 個 | 7 | 2.7 % |
| 7 個 | 2 | 0.8 % |
| 8 個 | 2 | 0.8 % |
| 9 個 | 1 | 0.4 % |
| **10+ 個** | 6 | 2.3 % |

大半 (73 %) の U1 クラスは Brother で **1 つの遷移先に統合される**。 10 個以上に分散するのは 6 クラスのみ (大きい U1 クラスに限定)。

### 6.5.3 サイズ上位 3 U1 クラスの個別遷移

#### `L0_U1_42656a5a` (size 172、 mode `$v0`) — 純粋な変数参照のみ

| 遷移先 | n_destinations | top 遷移先 | top 件数 / 172 | ratio |
|---|---:|---|---:|---:|
| Brother | **47** | `L0_U1_41efc340` (size 45) | 45 / 172 | 26 % |
| ExParent | **91** | `L0_U1_56a5aa22` (size 10) | 10 / 172 | 6 % |
| Parent | **101** | `L0_M2_0e34f3de` (size 1909) | 17 / 172 | 10 % |

→ **「変数参照 1 トークンのみ」 という構造は、 サイズを広げてもクラスがまとまらない**。 Brother で 47 個、 Parent では 101 個に分散。 Parent では 巨大 M2 クラス (size 1909、 多様な制御構文を含む) に吸収される。

#### `L0_U1_be4e182d` (size 62、 mode `$f0`) — 関数参照のみ

| 遷移先 | n_destinations | top 遷移先 | top 件数 / 62 | ratio |
|---|---:|---|---:|---:|
| Brother | 18 | `L0_M2_5c9d0e8f` (size 27) | 27 / 62 | 44 % |
| ExParent | 22 | `L0_M2_e73889f6` (size 30) | 24 / 62 | 39 % |
| Parent | 41 | `L0_M2_bd0e90c3` (size 12) | 6 / 62 | 10 % |

→ 関数参照は変数参照より多少まとまる (Brother で 44 %) が、 全体としては分散傾向。

#### `L0_U1_94c3289b` (size 50、 mode `unshift`) — 具体的なメソッド名

| 遷移先 | n_destinations | top 遷移先 | top 件数 / 50 | ratio |
|---|---:|---|---:|---:|
| **Brother** | **4** | `L0_M2_b2e24c8a` (size 50) | **47 / 50** | **94 %** |
| ExParent | 15 | `L0_M2_6f783a85` (size 23) | 18 / 50 | 36 % |
| Parent | 20 | `L0_M2_0e34f3de` (size 1909) | 21 / 50 | 42 % |

→ **メソッド名 `unshift` (具体的 API) はサイズを Brother に上げると 50 件中 47 件 (94 %) が同一 M2 クラスに集約**。 つまり 「`$v0.unshift($x)` という呼び出し全体」 として bigram 化されて、 ほぼ全員がまとまる。

### 6.5.4 観察のまとめ

U1 クラスのサイズ遷移の挙動は、 **1 トークンが何だったか** に強く依存する:

| 1 トークン種別 | 例 | サイズ↑時の挙動 |
|---|---|---|
| 具体的メソッド名 | `unshift`, `length` 等 | サイズ↑で **同一 M2 クラスに高純度で集約** (Brother で 90+ %)。 「メソッド呼び出し全体」 として再構成 |
| 関数参照 | `$f0` | 中程度に分散 (Brother で 44 %)。 関数本体や呼び出しコンテキストが多様 |
| 変数参照のみ | `$v0` | サイズ↑でも分散大 (Parent で 101 個に分散)。 「変数参照を取り囲む文脈」 が事例間で多様 |

### 6.5.5 paper への含意

> 「**1 トークンとして U1 クラスに集約された事例は、 サイズを広げると約 73 % が同一クラスに統合される (Brother) し、 Parent では 100 % が bigram あり M2 クラスへ昇格する**。 特に具体的メソッド名 (例: `unshift`) を持つ U1 クラスは Brother で 94 % の純度で M2 へ集約され、 「**メソッド呼び出し全体**」 として再認識される。 一方で純粋な変数参照のみの U1 クラス (`$v0` 等) はサイズを広げても多様な文脈に分散する」

これは paper §6.3.1 「サイズ・抽象度の組合せとパターンの関係」 で 「**1 トークンしか持たない事例は、 サイズを広げて bigram 化することで意味のあるクラスとして再構成できる**」 という主張の根拠となる。 提案手法の **サイズ可変設計** が、 unigram 集約失敗事例の救済にも機能していることを示す。

## 7. 考察

### 7.1 自動化の境界 (paper §6.2 への寄与)

E4 の数値は paper §6.2 「自動作成されたパターンは低速な要因を捉えているか」 の boundary を率直に示す:

- **集約 _不足_ の境界 = isolated**: τ=0.7 で 30 %、 τ=0.9 で 45 %。 ただし「単なる失敗」 ではなく **「希少な事例」** であり、 paper §6.3.2 「得られた新規パターン」 の母集団となる
- **集約 _過剰_ の境界 = 巨大クラス**: τ=0.7 L1 Parent で最大 3,356 件。 既知由来率が低いものは新規パターン候補かノイズか、 E6 で判定
- **対象外 (excluded)**: 約 130 件 (0.4 %)、 構造的に最小トークン未満で集約不能

### 7.2 旧 v6 の問題が v7 で解消された点

| 問題 | 旧 v6 | v7 (本タスク) |
|---|---|---|
| `L0_M2_9c43d97c` (size 1,487、 完全ノイズ) | 存在 | **消滅** |
| 空 bigram と短い事例の混同 | 1 クラスに吸収 | **excluded と U1 に分離** |
| 「集約できない事例」 の正体 | 単一 isolated と擬似クラスタが混在 | 純粋な isolated (希少構造) と U1 (1 トークン) に区別 |

これは paper §6.4 の妥当性脅威 「最小構造未満の事例の扱い」 を明示する材料になる。

### 7.3 共通 bigram 代表値の不在による制約

`_pattern_common_bigrams.json` が今回未生成のため、 巨大クラス (size ≥ 100) のうち 「全員共有 bigram がゼロ」 という擬似クラスタ判定ができない。 paper §6.2 「クラス数と集約されなかったもの」 では:

- **既知由来率 0 % のクラス (92 個)** を 「既知パターンに該当しない大規模集約結果」 として提示
- 個別の skeleton + mode_medoid (E6) で内容を確認し、 新規パターン or ノイズを判定

を 代替戦略とする。

> 提案手法によって集約に失敗する事例の性質を分析した。 まず、 1 メンバのみのクラス (isolated) は一律ベスト設定 (τ=0.7、 抽象化 0、 サイズ Diff) で 30.2 % (8,973 件) であった。 これらの bigram 集合サイズの中央値は 16 で、 集約された事例 (clustered) の中央値 13 よりも大きい。 また bigram の平均文書頻度は isolated の方が低く (中央値 2,411 対 2,800)、 つまり 「**短いから孤立した**」 のではなく 「**希少な構造を含むため類似事例が見つからなかった**」 ことを示す。 これらは paper §6.3.2 で新規パターン候補として扱う対象となる。
>
> 一方で、 三本立て集約により 1 トークンのみの事例 (1,352 件、 Diff サイズ) は U1 クラス (unigram 完全一致集約) として独立に分離された。 全 U1 クラス (260 個、 Diff) のメンバには事前分析の既知 7 パターン正解事例は 1 件も含まれない。 また、 4 つの全サイズ depth で cutout が空となる事例 (129 件、 0.4 %) は集約対象外 (excluded) として明示分離した。 これらは数値リテラルの差替えや変数参照のみといった、 性能差要因として弱い断片であり、 paper §6.4 妥当性脅威で 「最小限の構造を持たない事例は提案手法の対象外」 と明記する。
>
> サイズ ≥ 100 の集約結果は 16 設計組合せ合計で 121 クラス得られた。 うち 92 クラスは既知パターン由来事例を含まない (= 既知パターンに該当しない大規模集約結果)。 これらは E6 で代表値と head 側の AST 構造を併記して新規パターン候補として個別分析する。
